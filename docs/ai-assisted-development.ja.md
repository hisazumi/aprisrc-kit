# AIと一緒にサービスのコードを書く

[English](ai-assisted-development.md)

## 共通サービスと汎用missionの区別

通常のサービス変更は`apps/pwa/src/missions/myService.ts`から始めます。
AIにはこのファイル、`service/studentService.ts`、`service/catalog.ts`と関連テストを渡してください。
以下は低水準mission・triggerの追加手順です。汎用missionはPlaygroundの
**Advanced controls**内で使い、共通サービスを止めてから実行します。
共通のサービス選択欄は`service/catalog.ts`で管理し、mission登録だけでは増えません。
共通パネルの質問回答と汎用の音声・LLM intent実行は別の経路です。
現行操作は[quickstart](challenger-quickstart.ja.md)を参照してください。


Webのチャットやコーディング支援AIを利用するAPRISRC Kit参加者向けの作業手順です。
教材のお題は含めません。どんなサービスを作るかは参加者が決めます。
まず[参加者向けセットアップ](challenger-quickstart.ja.md)を行ってください。
コードを反映・検証するローカル開発環境は必要です。AIの回答だけではサービスは動かず、
動作確認が済んだことにもなりません。

## 1. コードを頼む前に体験を整理する

「何を観測するか → どの条件・状態を判断するか → 何をするか → 何を表示・発話するか」を
書きます。完了条件、人やマーカーを見失ったときの動作、キャンセル方法も決めます。

変更対象を区別してください。

- 再利用するmission：基本は`apps/pwa/src/missions/`と`config/`を変更します。
- 専用のサービス画面や状態遷移：対象コンポーネントとテストも渡し、変更範囲を明示します。
- 機体との接続：missionの変更ではなく、別途基盤・Adapterの作業として扱います。

missionを登録すると`/playground`で利用できますが、`/service`のサービスフローや
Playgroundのサンプルに自動追加されるわけではありません。

## 2. 小さく、現状に合った資料セットを渡す

[AIに添付する技術メモ](ai-service-context.ja.md)、そこに挙げた現在のソースファイル、
サービスの要件を添付します。リンク先や非公開ファイルをAIが取得できるとは限らないため、
GitHubのURLだけでなく内容を渡してください。貼り付ける場合はコードブロックごとに
リポジトリ内のファイル名を明記します。不足するimport先は、質問されたら追加します。

`git rev-parse HEAD`で対象コミットを記録します。`git status --short`と、関連する変更済み
ファイルの現状も渡します。コミット番号だけでは未コミットの変更は伝わりません。
`.env`、`.certs`、アクセストークン、SSH秘密鍵、未確認の実行ログは添付しません。
エラーを渡す前にも、個人情報や認証情報を取り除いてください。

リポジトリ全体をそのままアップロードする必要はありません。依存ライブラリ、生成物、
秘密の設定が混在し得ます。技術メモの最小ファイル一覧を使ってください。

## 3. 変更範囲を決めて依頼する

以下を埋め、ファイルと一緒に渡します。

```text
APRISRC Kitでサービスを開発しています。
対象コミット：<番号>。関連する未コミット変更：<内容、またはなし>。
目的・利用者の体験：<説明>。
観測 → 条件・状態 → 行動 → 表示・発話：<説明>。
完了・キャンセル・対象喪失時の動作：<説明>。
変更してよいファイル：<パス>。対象画面：</playground、または明示したコンポーネント>。
検証環境：Simulatorのみ。

添付した技術メモとソースを最初に読んでください。
存在しないAPIを作らず、不足するファイルは推測せず質問してください。
指定範囲内で変更し、範囲を広げる必要があれば理由を説明してください。
変更ファイル名と差分（または小さい変更ファイルごとの全文）、テスト、
具体的な確認手順を返してください。
実行済みの確認と、私がローカルで実行すべき確認を分けてください。
今回、通信・安全上限・依存関係・ファームウェアは変更しないでください。
```

既存ファイルの全文を置き換える場合も、無関係なコードや既存の登録を消さないようにします。
適用前に差分を読み、ブランチやチェックポイントを用意してください。
他の作業を巻き戻さずに、今回の変更だけを確認・取り消せるようにします。

## 4. ローカルで反映して確かめる

[quickstart](challenger-quickstart.ja.md)に従ってSimulatorを明示的に選び、実行前に
`/api/status`の`adapter_type`が`simulator`であることを確認します。
ポートやHTTPSの有無は環境で異なるので、起動時に表示されたURLを使ってください。
自分の開発テストのために、共用の実機サーバーを切り替えないでください。

リポジトリのルートで実行します。

```sh
npm run typecheck --workspace @apris/pwa
npm run test --workspace @apris/pwa
npm run build --workspace @apris/pwa
```

狭い変更でも、どの既存・追加テストが変更内容を確かめるかを確認します。
その後`/playground`で正常完了、キャンセル、観測喪失・古い観測、繰り返し実行を確認します。
`/service`を変更したなら、そのフローも別途確認してください。
型チェックの成功はサービス動作の証明ではなく、Simulatorの成功は実カメラの揺らぎ、
Wi-Fi、制動、実機での動作を保証しません。実機試験は運用手順と走行前の許可が必要です。

## 5. 結果をAIへ返す

実行したコマンド、正確なエラー、期待した動作と実際の動作、Adapter種別、変更ファイルの
現状を渡します。画面の問題にはスクリーンショットも有効ですが、エラー本文も添えてください。
動かない場合は接続、操作権、非常停止、観測状態を伝え、安全機構の迂回を頼まないでください。

コミット前に`git diff`を確認し、秘密情報・生成物・無関係な変更が入っていないか見ます。
実際に確認した範囲と未確認の範囲を記録してください。
詳細は[Mission API](mission-api.ja.md)、[行動の登録](adding-actions.ja.md)、
[現在の対応状況](platform-status.ja.md)を参照します。
