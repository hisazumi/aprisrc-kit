# 連続追従の実機試験準備（実験的）

[English (canonical)](continuous-follow-trial.md)

短時間の監視付きiron-X実機試験は後述のとおりですが、すべてのネットワークでの安定性を保証しません。
Simulatorでは実カメラの揺れ、Wi-Fi遅延、制動性能まで評価できません。

Simulatorは上限0.25 m/s・距離ゲイン0.8の連続P制御を使います。
`ironx_network`もP制御＋加減速制限の連続追従が標準です。
UGV02・同一ホストiron-Xは変更しません。

## 従来方式に切り替える

まずサービスを停止します。連続追従をオフにするには、PWAを起動するターミナルで
起動前に設定します（Windows PowerShell）。

```powershell
$env:VITE_IRONX_CONTINUOUS_FOLLOW = "0"
```

macOS/Linuxの場合：

```sh
export VITE_IRONX_CONTINUOUS_FOLLOW=0
```

[PC・iPhoneの既存手順](ironx-follow.ja.md)に従い、PCサーバーは`ironx_network`を使います。
この設定は制御方式を選ぶだけで、走行許可ではありません。開発時はViteを再起動し、
サービス停止中にスマホを再読み込みします。配布版PWAは設定変更後の再ビルドが必要です。

実機プロファイルは前進上限0.15 m/s、距離ゲイン0.6です。
共通の既定値は旋回上限0.2 rad/s、加速度0.12 m/s²、減速度0.3 m/s²、
角加速度0.5 rad/s²です。喪失・故障による停止では通常の加減速制限を迂回します。
サーバーの操作権、前方確認、非常停止、指令有効期限は維持します。
速度APIの応答は送信完了であり実際の動作完了ではありません。物理停止を操作できる状態にします。

操作者の許可後、短い前進追従、左右への追従、人の停止、対象喪失の順に確認します。
指令速度・観測速度・停止距離を記録し、停止を確認する前に最高速度を上げないでください。

ネットワーク接続のiron-Xでは、`0`だけが従来のmove/turn追従を選択します。
標準の連続追従に戻す場合はサービスを停止し、設定を削除します。

```powershell
Remove-Item Env:VITE_IRONX_CONTINUOUS_FOLLOW -ErrorAction SilentlyContinue
```

macOS/Linuxでは`unset VITE_IRONX_CONTINUOUS_FOLLOW`を使います。
Viteの`.env`ファイルに書いた場合はそちらの設定も削除してください。
`1`を設定しても連続追従になります。どちらの変更でもPWAを再起動・再ビルドし、
スマホを再読み込みします。
再接続だけでサービスを再開しません。ソース設定やソフトウェアテストの成功は、
実機への配備・動作確認を意味しません。

## 学内試験（2026-11-01）

初回は約1.3秒の右旋回出力の後、走行応答のタイムアウトで停止しました。
前進出力はなく、その後の観測速度はほぼゼロに戻りました。追従成功の確認ではありません。
SSH経由の状態取得40回では往復時間の中央値9.75ms、最大106.3msでしたが、
先の250msタイムアウトの原因を特定するものではありません。

PC側の走行応答待ちを最大1秒に分離しました。指令の有効期限200msと
ゲートウェイ操作権の有効期限300msは変更していません。通信が遅ければ停止・中断します。
100ms以上かかった応答は処理名と所要時間を記録します。
停止・操作権返却・切断時の停止確認失敗は、非常停止を保持して`stop_unconfirmed`を通知します。
停止済みと報告したり、クライアントの後処理を例外で中断したりしません。
遅延応答・停止失敗の自動テストは通過しましたが、実機での再確認は必要です。
共用ネットワークではSSHトンネルまたはTLSを使用してください。

### 追加の通信・復旧改善（実機再検証待ち）

走行応答に観測状態と次回用の使い捨て確認情報を含めます。PCは通信時間を含む
保守的な経過時間が100ms未満の場合だけ次の指令に利用し、古ければ状態を取り直します。
これにより連続指令では原則1往復を省きますが、指令・確認情報の期限は延ばしません。
旧ゲートウェイには従来方式で接続します。停止・通信異常時には保存した情報を破棄します。

通信断後は、再接続して操作権がないだけでは停止確認済みと扱いません。
次の停止要求では実機側の非常停止確認応答を必須にし、再開には明示的な解除を求めます。
指令期限切れ時の停止確認に失敗しても安全監視を例外で中断せず、停止未確認を通知します。
保守時はゲートウェイの`--start-estopped`で非常停止を保持して起動できます。
Wi-Fi構成とSSHトンネルはそのままです。ネットワーク自体の揺らぎが解消したという意味ではありません。

### 通信診断ログの読み方

セッションJSONLの`adapter_command`には、指令の成功・失敗時に`transport`を記録します。
指令ロック待ち、全体の所要時間、保存した応答の経過時間・再利用の有無、送信準備時間、
残りのTTLを含みます。各RPCにはリクエストID、処理名、RPCロック待ち、送受信時間、
応答期限、結果、拒否時の実機側エラーコード・説明を記録します。
引数・使い捨て確認情報・トークンは記録しません。失敗時はブラウザ指令の連番と
例外の詳細も残します。遅いRPCと失敗RPCはサーバーログにも出力します。
計測の開始点はPCサーバーで、ブラウザやWebSocketの処理前バッファ、Wi-Fi片道遅延は別計測していません。

模擬テストでは、並行する状態取得の320ms遅延が走行指令を待たせ、`lease_expired`で
拒否される条件を再現しました。これは仮説の裏付けであり、前回の実機停止原因の確定ではありません。
当時のログには実機が返した詳細がないため、次の許可された試験で追加項目を照合します。

その後の許可された試験では、約272msの状態取得の後、`release`が`not_owner`で拒否され、
拒否応答自体は約10msで届きました。操作権失効と整合しますが、通信断の証拠ではありません。
PCが操作権を保持している認識のときに受けた`not_owner`、`lease_expired`、`expired_nonce`は、
通信断と区別します。接続を維持し、保存した指令情報を破棄して再開禁止を保持し、
停止要求では同じ接続を使って実機側の非常停止確認へ進みます。
返却時の失効拒否なら直ちにこの確認を行います。操作権の自動再取得はしません。
停止確認が失敗すれば未確認のままです。最初から操作権を持たないクライアントの取得拒否は
この回復処理の対象にせず、この経路で別の操作者を停止させないようにします。
模擬テストで確認済みですが、実機での再検証は必要です。

### その後の監視付き実機試験

2026-11-01、Macをeduroamに戻してSSHトンネルを復旧した後、操作者から
概ね追従できているとの報告がありました。約14.5秒間の走行要求261回がすべて成功し、
235回で直前の応答を再利用しました。Adapterでの指令処理時間は中央値14.2ms、
最大140.3msでした。車輪由来の位置推定で変位約0.82mとなりましたが、外部実測値ではありません。
この区間では操作権失効・通信エラーによる中断はなく、サービス停止要求で終了し、
その後の観測速度はほぼゼロでした。終了時にはTTL期限切れによる停止も記録され、
操作権返却後に`not_controller`応答が1件ありました。

指令間隔が200msを超えた箇所は2回（最大約235ms）あり、常に滑らかな動作や
長時間のネットワーク安定性を証明するものではありません。この構成での短時間・監視付き追従の
確認であり、操作権失効からの回復を意図的に試した試験ではありません。
サーバーテストは279件通過。根拠はPCセッション`session-20261101-112524-77171b.jsonl`の
タイ時間11:33:39〜11:33:54頃の走行区間です。認証情報や生のセッションログはコミットしません。
