# iron-Xの監視付き操作

[English (canonical)](ironx-quickstart.md)

2026-10-31時点の実験的なiron-X Pro Max / ROS 2 Humble対応。
通常の操作はこのガイドから始め、契約・試験記録は[Adapter詳細](ironx-adapter.md)を参照する。
UGV02は引き続き基準ハードウェアである。

## 確認できた範囲

1台で状態表示、Adapter経由の動作・停止・キャンセル、床上の短距離移動と旋回、
コンソールの手動確認を使った走行を確認した。10cm前進2回の推定値は9.638/9.634cm、
左15度旋回の推定値は14.911度。目視では妥当との報告だが、精密測定ではない。
iron-Xでの人追従・マーカー案内・サービス画面の実機検証は未完了。
Live PlaygroundのUGV02向け判定が`ironx`を受け付けるかも、別途確認が必要である。

## 起動前提

- Ubuntu 22.04 / ROS Humble。Kitサーバーは別のPython環境で動かす。
- driverの`/cmd_vel`を`/apris_readonly/no_commands`へ分離し、車輪計測は
  `/wheel/odometry`、EKF出力は`/odom`を使う。
- driverは1つだけ。full bringup、Node-RED等の走行送信者、診断用probeを重複実行しない。
- 電源・物理停止を操作できる状態にし、前方だけでなく左右・後方も空ける。
  動かす前に操作者の許可を得る。無人運用を目的とした構成ではない。

ROS側の前提は[読み取り専用表示](ironx-readonly.md)を参照。
新規ROS環境構築やファーム書き換えの手順ではない。

## 起動と切り替え

英語正本のコマンドを使用する。`ROOT`は実機上のcheckoutディレクトリである。

1. 同一ホストの非公開runtimeディレクトリを用意し、`npm run build`を実行する。
2. telemetry bridgeを起動する。既に動いている場合は追加起動しない。
3. 最初は`ros2_readonly`で表示を確認する。`/ros2`には走行操作はなく、物理停止の代わりにもならない。
4. 走行切り替えの許可後、読み取り専用Kitサーバーだけを停止する。ROS・telemetry・SSHは維持する。
5. command bridgeの非走行チェック後、専用端末で`--enable`を付けて起動する。
6. 別端末で`APRIS_ADAPTER=ironx`と3つの絶対ファイルパスを設定してKitサーバーを起動する。
7. `/api/status`で`ironx`、接続、速度ゼロを確認し、実機アドレスのport 8000で`/console`を開く。

## コンソール操作

1. 1つのタブで操作権を取得する。
2. 周囲を確認して **Confirm clear path · 30 s** を押す。
   前方の手動確認を送る操作であり、それだけでは走行しない。
3. ジョイスティックを押している間だけ走行し、離すと停止する。
   初期上限は5cm/秒、約11.5度/秒。
4. 30秒経過、接続断、操作権喪失、E-stop、障害物検知、タブ非表示、ウィンドウのフォーカス喪失、
   明示解除、画面離脱で確認を解除する。再確認時は周囲を見直す。
5. 停止後に操作権をサービスへ渡す。ソフトウェア停止が効かなければ物理停止・電源を使う。

`front_obstacle_unknown`は新しく正常な前方安全情報がないという意味。
確認ボタンは既存APIに期限付きの`manual`観測を送り、Adapterが`CLEAR`を偽装するものではない。
現在のチェックは前進のみで、後方・側方の衝突防止は未実装。全方向を人が監視する必要がある。
追加ボタンはコンソール限定で、サービスやPlaygroundは既存の確認操作を維持する。

## 終了と制約

停止と速度を確認し、Kitサーバー、command bridgeの順で終了する。
fault状態のbridgeは、停止と競合送信者の除去を確認してから再起動する。
画面更新が反映されない場合はキャッシュを避けた再読み込みを行う。

指令有効期限は最大300msだが、実際の制動・停止確認には追加時間がかかる。
bridge・OS・シリアル自体の故障はこのwatchdogでは保護できない。
次は監視付きのサービス試験であり、安全確認を無効化して進めない。
