# iron-X通信遅延のオフライン再現実験

[English (canonical)](ironx-delay-reproduction.md)

## 本番との分離

**現在の実験設定：** 操作権だけ2秒（`OWNERSHIP_LEASE_SECONDS`）に分離しました。
nonceは300ms（`NONCE_SECONDS`）、PC側指令TTL上限は200msのままです。NOP・heartbeatは
追加していません。実機側gatewayは**未更新・未再起動**で、配備済みの操作権は300msのままです。
以下の従来の300ms実験は履歴で、該当テスト内だけ定数を一時的に上書きして維持します。

`5c7844d`から分けた`experiment/ironx-delay-reproduction`ブランチの実験です。
別worktreeで実施し、本番のサーバー・環境変数・作業フォルダ・SSH・実機には触れません。
復旧処理の分類修正は実験用worktreeだけに適用します。本番コード・安全閾値・速度上限・
指令TTLは変えません。本番前のマージ・配備はしません。

11月1日のログにあった操作権失効（`not_owner`）と、`stopping`応答を通信断扱いする
経路を再現します。実際のパケット時系列を完全再生するものでも、すべての停止原因を
確定するものでもありません。生ログ・秘密のトークン・実機アドレスは含めません。

## 実行方法

実験用worktree内で、Python 3.11以上とサーバーの開発用依存を使います。
Windows PowerShell：

```powershell
cd apps/server
uv sync --group dev
$env:PYTHONPATH = "src"
uv run pytest tests/test_ironx_delay_reproduction.py -v
```

macOS/Linuxでは環境変数を`export PYTHONPATH=src`で設定します。
同じテストを繰り返して、実行タイミングによるばらつきも確認できます。
関連テストを含める場合：

```sh
uv run pytest tests/test_ironx_delay_reproduction.py tests/test_ironx_network_adapter.py tests/test_ironx_gateway.py -q
```

接続先は**127.0.0.1の自動割り当てポートだけ**です。固定のテスト用トークンを使い、
実機URL・ROS設定・mailboxファイルは読みません。各試験後に一時サーバーと監視タスクを
終了します。ブラウザー・iPhone・SSH・実機は不要です。実行環境でローカルソケットが
許可されている必要があります。

## 再現した条件

本番と同じAdapter・GatewayをローカルWebSocketで接続し、テスト専用Gatewayで
要求の処理前・応答の返送前に遅延を入れます。操作権の監視は本番コードを使います。
ロボット部分は指令・停止呼び出しを記録するだけの模擬実装です。

| 条件 | 結果として検証する内容 |
| --- | --- |
| 走行応答に10、20、40、10、20msの遅延、呼び出し間に20msの待ち | 5指令が成功し、再許可不要。明示停止で操作権を返却。 |
| 初回指令後160ms待ち、次の状態応答を180ms遅延 | 300msの操作権が失効。次の指令が`not_owner`で拒否され、同じ接続で停止確認。自動再走行なし。 |
| 次の走行要求を360ms遅延し、模擬停止確認をイベントで待たせる | 監視が停止を開始。元のコードでは`stopping`応答を通信断扱い。実験用修正では接続を維持して停止確認を待ち、再走行には明示解除を要求。 |
| 状態応答を400ms遅延 | 状態取得がタイムアウト。模擬ロボットへ走行指令は届かず、再走行も拒否。 |
| 操作権のないクライアントが停止中に取得を要求 | 停止確認を要求せず、別の操作者の機体を停止させない。 |

「停止確認中」のテストで元の不具合を再現した後、実験用修正の回帰テストに変更しました。
自分が操作権を保持していると認識する走行要求の`stopping`だけを分類し、接続を維持して
古い指令情報を破棄、再走行を禁止して停止確認に進みます。模擬停止を待たせている間は
確認済みにならないことも検証します。停止待ちイベントは後処理で必ず解除します。
本当のタイムアウトは従来の通信障害処理のままです。操作権失効やネットワーク自体の問題を
解消したわけではなく、誤った通信断扱いを避け、残った接続で停止を確認できるようにします。

## 限界と本番後の作業

実行記録（2026-11-01、macOS、Python 3.12.13）：4条件すべて通過し、追加の3回も
各4件通過（1回1.24〜1.26秒）。既存のnetwork Adapter・Gatewayと合わせて69件通過
（9.46秒）、追加テストのRuffも通過しました。本番用checkoutは`5c7844d`のままで、
追跡対象ファイルに変更なし。本実験では本番の再起動・SSH操作・実機走行を行っていません。

実験用の復旧修正後はサーバーテスト284件が通過（31.49秒）、変更したPython 2ファイルの
Ruffも通過しました。操作権なしの場合は既存の取得失敗経路（ローカルの停止エラーを含む）を
維持し、遠隔停止を送らないことを検証しています。拒否応答全般の分類は今後の課題です。
mainへのマージ、本番サーバーへの配備は行っていません。

## 不要な待ちによる操作権失効の削減

`750f811`に最初の再現実験と停止中応答の修正を保存しました。
次の実験用変更では期限を延長せず、表示のための重複した状態取得を減らします。
PCが操作権を持ち、経過時間を加算した状態が100ms未満で接続正常の場合だけ、
表示に再利用します。新たな状態RPCが次の走行指令を同じ通信ロックで待たせるのを避けます。
再利用しても取得時刻や操作権期限を更新しません。古い状態・待機中・再許可が必要な場合は
この近道を使わず、既存の指令処理中のポーリング動作も維持します。

追加テストでは初回走行後、独立した状態応答に320msの遅延を入れます。
修正前は不要な状態RPCを送り、状態が古くなって操作権も失効しました。
修正後は20ms間隔で12回の表示・走行サイクルを続け、余分な状態取得をせず合計13指令が
成功することを検証します。120ms経過した状態は取得し直すこと、待機中は通常のRPCを
使うことも別テストで確認します。

これは走行通信自体の任意の320ms遅延を許容する変更ではなく、失効を完全に防ぐものでも
自動で操作権を再取得するものでもありません。元の状態遅延・走行遅延・タイムアウト試験は
引き続き停止・拒否が必要です。操作権300ms・指令TTL上限200ms・状態鮮度の閾値・速度上限は
維持しています。状態取得用の別接続や通信順序の再設計は、今後の検討課題です。

変更後の確認：サーバーテスト287件通過（31.93秒）、最終の遅延実験8件通過（1.71秒）。
表示への再利用で操作権期限・保存した取得時刻が変わらないことも検証しました。
Python 2ファイルのRuffも通過。オフラインの結果であり、実機検証や大学のネットワークでの
安定性を示すものではありません。

## 操作権だけ2秒にする実験

これまで共用だった操作権とnonceの定数を分離しました。nonceの発行時刻の逆算も
300msの定数を維持します。取得時・成功した走行時だけ操作権の期限を2秒先に設定し、
状態取得・同じ所有者の再取得要求・失敗した走行では延長しません。明示的な返却、
切断、非常停止、走行拒否時の停止処理は変更しません。

追加の確認項目：

- 模擬時計で1.999秒は保持し、2秒ちょうどで失効。それまでは別の操作者の取得を拒否。
- 400ms・1.5秒の空白後も同じ操作権で**新鮮な**nonceと指令を受け付ける。
  ローカルWebSocketでも400msの空白後に確認。
- 操作権が有効でも、300msを超えた古いnonceは拒否。
- 実際のmailbox書き込み・command bridgeの期限処理を一時ファイルと模擬観測で実行。
  200ms指令が210ms時点ではゼロ出力になり、400ms時点でも操作権は保持されることを確認。
  ソフトウェア出力の検証であり、車輪の実停止時間を測ったものではない。
- 既存の失効テストは2秒を待つよう変更。従来300msでの再現は該当テスト内だけ条件を固定。

残る問題：バックグラウンド状態取得が320ms遅れると古いnonceが削除され、待機していた
走行指令に`invalid_nonce`が返ります。PCの既存処理はこれを通信障害扱いします。
今回のテストはこの未修正の挙動を記録するもので、操作権延長による解消は主張しません。
指令が拒否された場合の既存経路では操作権が取り消されることもあります。
2秒への延長だけで追従が途切れなくなるわけではありません。

検証結果：一時mailboxの期限テストを含むサーバーテスト293件が通過（38.53秒）。
変更したPython 6ファイルのRuffも通過しました。この作業では稼働中Gateway・サーバーの
再起動、遠隔配備、非常停止解除、走行は行っていません。

- 固定の遅延条件と実時間を使います。パケット損失や実ログの完全再生ではなく、PCの負荷で
  タイミングが変わる可能性があります。
- 模擬ロボットは静止状態を返します。車輪の物理・モーター側TTL監視はモデル化していません。
  指令TTLやGatewayの停止処理を確認しても、停止距離・制動・滑らかさの検証にはなりません。
- カメラ、ブラウザーからPCまでの通信、SSHのバッファ、Wi-Fi自体は模擬していません。
  Gatewayの拒否応答を受信したことと、無線通信が切れたことは区別します。
- 本番後に、停止中・失効の拒否応答と通信障害を区別する処理、古い指令の破棄、停止確認を
  この再現テストで検討します。タイムアウトの延長を先に行うものではありません。
- 配備と実機の停止確認は別途必要です。本番用の構成はそのまま維持します。
