# コンソールからのサービス開始・停止・再実行

[English（正本）](managed-service.md) · [接続方式](connected-service.ja.md)

運用サーバが固定の `console-service.ts` をNode子プロセスとして管理する。
移動の最終権限は従来と同じPython runtimeにあり、二つ目のSimulatorは起動しない。
画面から実行ファイル・任意のコード・引数を指定する機能は設けない。

## 操作

リポジトリのrootで起動する。Node（既存試作と同じ対応版）をPATHに置く。

```sh
uv sync --directory apps/server --frozen
uv run --directory apps/server python -m apris_server.operator_console
```

1. 表示された `/console` と `/app` のURLを開く。
2. コンソールで操作権取得、合成の前方CLEAR入力、退避確認、明示復帰を行う。
3. **「サービス開始」**を押す。端末でNodeを別途起動する必要はない。
4. サービス画面で人物検出・質問・積載・到着に回答する。
   積載時の退避確認・guard解除はコンソールで別に行う。
5. 正常終了後はコンソールの**「再実行」**で新しいrunを開始できる。
6. **「サービス停止」**はrunを失効し、移動禁止を保持してNodeを終了する。
   受け渡しguardがある場合は残る。再実行前に停止完了と明示復帰が必要。

既存の「試験runを開始」は手動move／turn試験用で、サービス開始には使わない。
サービス起動中は手動run開始も無効化する。全体停止は引き続き有効で、起動途中のNodeも停止する。

## 生命周期と制約

一度に管理するNodeは一つ。起動中・実行中・停止中は二重起動を拒否する。
起動要求ごとにlaunch ID、サービスごとにrun epochを発行する。
Nodeの受付は予約したlaunch IDと運用者を照合し、起動前の停止や別の運用者への変更を拒否する。
古い停止要求は新しいlaunchに作用せず、古い質問・回答は新しいrunへ引き継がない。
プロセス終了時の後処理も、そのプロセスが所有したrunにだけ適用する。

停止はまずPythonの操作権を失効させ、Nodeに終了を要求する。
700 msで終了しなければkillを試み、終了確認にも上限を設ける。
プロセス終了・出力読取りには上限があり、出力は4 KiBの末尾だけを保持する。
Node不在・起動失敗もコンソールに表示し、過去の正常終了表示で隠さない。
プロセスを再起動して自動的にrunを再開する処理はない。

これはソースcheckoutから起動するSimulator専用構成。Node hostのファイルも必要。
通常の起動先は127.0.0.1:8766。試験用に別のloopback portを指定する構成も可能で、
管理されたNodeには同じ接続先を渡す。物理rover・複数サービス・役割別認証は未対応。

## 検証

Node全148件、運用APIのPython8件、TypeScript、Ruffがローカルで成功。
実プロセスの結合試験では、起動直後の停止、二重起動拒否、正常終了、再実行、
新しいrun・質問、古い回答と停止要求の拒否、受け渡し中停止後のguard保持・再実行拒否を確認した。
Node実行ファイル不在のAPI試験と、ボタンの有効条件・起動失敗表示のDOM試験も追加した。
実ブラウザの表示と実機の停止を新たに認定したものではない。

再現試験は[サービスの再現シナリオと実行記録](service-scenarios.ja.md)を参照。
