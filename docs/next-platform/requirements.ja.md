# 次期プラットフォーム：要求たたき台

[English（正本）](requirements.md)

状態：議論用のたたき台、2026-11-05。次期APRISRC Kitへの要求案であり、実装済み機能、競技ルール、技術の採用決定ではない。範囲を確認した後、アーキテクチャへ具体化する。

## 1. 目的と対象範囲

学生が位置推定、機体通信、接続基盤を各班で繰り返し実装することなく、移動・認識・対話を組み合わせたサービスを設計・実装・評価できるようにする。

大まかな要求を先に整理し、責務・インターフェース・可変点・実行配置を設計する。不確実な点は小さな一連の試作で検証する。現行部品の全面的な作り直しは前提としない。

初期対象は、準備した地図と登録経路を使う、監督付きの屋内サービス試作とする。積み下ろしや確認を人が担ってよい。以下の3例は要求の抜けを確認する代表例であり、学生の課題や解答を指定するものでも、将来の全サービスを網羅するものでもない。

## 2. 利用者と責任

| 役割 | 責任 |
| --- | --- |
| 学生開発者 | 解決する問題、サービス方針、行先、認識条件、対話、評価を設計 |
| 利用者・担当者 | サービスの依頼、通知の受領、受け渡し・作業完了の確認 |
| 教員・運用者 | 環境・機体の準備、試験の監督、操作権の管理、障害復旧 |
| 基盤開発者 | 共通能力、アダプタ、実行契約、配布環境、診断を提供 |

サービス上の判断は学生が持ち、基盤は仕組みと再利用可能な標準部品を提供する。例えば「ボトルの観測」は基盤、「清掃案件とするか」はサービスの判断とする。サービスの判断で走行保護を解除してはならない。

## 3. 代表シナリオ

### S1：巡回・検出・通知

1. 運用者の操作、または設定した定期タイマーで巡回を要求する。既に巡回中の場合は、明示した重複起動方針に従う。
2. ロボットが登録地点を巡回しながら物体観測を監視する。
3. サービスで選んだ条件に合えば、画像・観測時刻・部屋名や巡回地点を含む報告を作る。
4. 別画面の担当者が報告を受け取り、受付・対応完了を登録する。
5. サービスの方針に従って巡回を継続または一時停止する。

初期は既知の物体1種類でよい。物体の厳密な世界座標は要求しない。繰り返し検出で無制限に案件が増えないようにする。観測の欠落・古さ、位置不確か、通知失敗、中止を明示する。実際の清掃動作は対象外。

### S2：配送・受け渡し

1. 利用者が名前付き地点間の配送を依頼する。
2. 人が荷物を積み、準備完了を確認する。
3. ロボットが登録経路で目的地へ移動する。
4. 受取人が受領を確認し、サービスが案件を完了して帰還または待機する。

到着と受け渡し完了を区別し、確認がない配送を成功にしない。配送中にも新規依頼を受け付けられるようにするが、初期の配送実行は順番に1件ずつでよい。ロボットによる積み下ろしは要求しない。

### S3：同行者を確認しながら案内

1. 依頼または人の観測をきっかけに対話を開始する。来訪者が支援を希望することを確認し、直接または物品の選択を通じて目的地を決める。
2. ロボットが登録経路を先導し、来訪者がついてきているか確認する。
3. 来訪者が遅れたら待機し、明示した条件で再開する。
4. 到着を案内するか、案内が中断したことを知らせる。

先導と追従を区別する。同伴確認は初期には明示的な確認入力でもよく、画像による自動確認は差し替え候補とする。同行者を見失った状態を案内成功にしない。

支援を断られた、対象物が見つからない、行先が未対応といった場合には、選び直し、スタッフへの案内、拠点への帰還をサービスで選べるようにする。これらの業務上の分岐と走行障害を区別する。帰還も通常の移動契約に従い、停止状態や危険条件を無視して走行を再開しない。

### 組合せと既存の追従機能

先導に加え、人追従を対応する参照能力として維持する。組合せ例は「客に追従してテーブルへ移動→選んだ席を確認・記録→注文と確認→厨房からその席へ配送」とする。第4の大シナリオを追加せず、S2・S3の能力を組み合わせて検証する。

追従対象の喪失、キャンセル、追従から経路移動への切替を定義し、終了した活動が移動の操作権を保持しないようにする。

### シナリオ条件の出自

巡回・通知、定期巡回、配送・受け渡し、物品・棚の選択、人を発見しての支援開始、追従、注文、スタッフへの案内は2026年度の発表シナリオに根拠がある。ただし、報告された構想・手順であり、実装を独立に検証したことを意味しない。

同行者が遅れた場合の待機、画面での清掃対応完了登録、配送中の新規依頼受付は、協調動作と状態管理を確かめるために追加した次期向けの条件である。原発表の明示的要求とは扱わず、初期実装の範囲は引き続き検討する。

## 4. 機能要求

**必須**は初期の代表サービス範囲に必要なもの、**拡張**は後段で扱うもの。必須でも全実装バリアントを用意する意味ではない。

| ID | 優先度 | 要求 | 確認方法 |
| --- | --- | --- | --- |
| F01 | 必須 | 名前付き地点、経路、初期位置、既知マーカーの姿勢・実寸を含む共通マップを読み込む。選択したモデルに応じて壁・進入禁止領域を表す | 保存した環境をシミュレーションと実機試験で再利用し、座標系を説明できる |
| F02 | 必須 | 位置・向き・推定品質を提供する。基準構成ではオドメトリを疎な既知マーカーで補正する | 指定経路でドリフト・補正・推定不能／品質不足時の挙動を測る |
| F03 | 必須 | 登録経路による目的地移動・巡回・帰還を提供し、到着・失敗・中止を区別する | S1・S2を、サービス固有の車輪指令や時間旋回の調整なしで実行する |
| F04 | 必須 | 人・マーカー・選択物体の検証済み観測を提供し、入力元・時刻・利用可能な信頼度／品質を付ける | 疑似・録画・実入力に共通契約を用い、不正・古い観測を区別できる |
| F05 | 必須 | シーケンスと並行活動、宛先を持つイベントを組み合わせ、活動の寿命を定義する | 巡回監視とS3の待機が成立し、サービス終了で従属活動も終わる |
| F06 | 必須 | 長時間処理の開始、意味のある進捗、完了、失敗、キャンセルを定義する | 中止要求受付と停止確認を区別し、遅れて届く結果で処理を再開しない |
| F07 | 必須 | 役割・画面をまたぐ構造化された依頼、入力検証・再確認、通知と、変更可能なサービス画面を提供する。画面・音声等の手段を選べるようにする | S2の受領確認とS1の通知を、利用者へ運用操作を露出させずに実現する |
| F08 | 必須 | 案件ID・状態の仕組みを提供し、業務遷移・重複処理を設定可能にする | 繰り返し観測・確認を明示した方針で扱い、中断を成功にしない |
| F09 | 必須 | 対応能力を持つSimulatorと実機で同じサービスロジックを実行する | 対応バックエンドの切替を設定・アダプタで行い、専用サービスへ書き直さない |
| F10 | 必須 | 初期条件の保存、シミュレーション時刻、一時停止・再開・リセット、故障シナリオを提供する | 入力・時間条件を明示して反復し、制御できない変動要因は明記する |
| F11 | 必須 | 現在の動作、観測、待機条件、接続先、停止・失敗理由、関連する時間情報を示す | 開発者が参照サービスの待機・停止理由を説明できる |
| F12 | 拡張 | 自由経路計画、高度な自律化、追加センサーに対応する | 登録経路でのサービス成立後、別途評価する |
| F13 | 必須 | 手動依頼・観測・定期タイマーを開始条件の可変点として明示し、初期対応方式と重複起動方針を定義する | 実行中の開始要求を方針に従って受理・待機・拒否し、繰り返し観測で黙って二重起動しない |
| F14 | 必須 | 人追従を維持し、対話・経路移動と組み合わせられるようにする | 追従・注文・配送の例で移動操作権を競合させずに切り替え、対象喪失・キャンセルの結果を明示する |

F13は開始条件の契約と初期対応範囲の明示を要求し、全方式の即時実装や汎用スケジューラを要求しない。対話には画面・ボタンによる代替を認め、F07は特定の音声プロバイダや自然言語理解を必須にしない。

マップ、位置推定、経路計画、障害物回避は別能力である。壁の描画だけで衝突・検知を実装したと扱わず、各Simulatorの意味を定義する。物体検出は距離推定・同一性追跡を自動的に保証しない。

F08の再起動をまたぐ永続化と保持期間は未決定。初期は中断状態と復旧方針を明確にすることを要求し、汎用業務データベースは要求しない。

## 5. 品質・運用要求

| ID | 要求 | 確認方法 |
| --- | --- | --- |
| Q01 | 操作権、指令期限、速度制限、通信断停止、非常停止を維持し、実際の接続先を明示する。復旧で自動走行再開しない | 不明／再接続先、競合指令、中断を試験。物理的停止性能は別途測定 |
| Q02 | 版を固定した再現可能な環境と、簡単な起動・停止・リセット・復旧を提供する | 初見の利用者が代表的な新規PCで説明に従い起動・復旧できる |
| Q03 | 実行の寿命をブラウザの偶発的な状態から分離して定義する | 画面終了・バックグラウンド化・スマホ休止・再接続を試し、案件を二重起動しない |
| Q04 | センサー・機体・ミドルウェアの詳細を共通能力の契約に隠す | 二つ目のサービスへプロトコル知識なしで転用し、未対応能力を明示する |
| Q05 | 環境交換をまたいで学生のコードと成果を復元可能にする | 環境更新・復旧の試行で学生の作業が残る |
| Q06 | 実測、シミュレーション真値、推定値、疑似観測を区別する | 試験記録に入力元・構成を残し、仮想試験を実機検証と呼ばない |
| Q07 | 初期参照サービスはクラウドを必須にせず会場内で実行できる | 準備後にインターネットなしで実行し、任意のオンライン機能を区別する |
| Q08 | 性能・精度の制約を明示し、観測可能にする | 受入前に経路誤差、停止、観測の古さ、応答遅延、資源量の基準を設定・測定する |
| Q09 | 認証情報や不要な撮影データを露出せず、診断に必要な情報を提供する | 診断を秘匿化し、参照サービスの画像・報告へのアクセスと保持期間を定義する |

実機watchdogには実時間の単調時計を用いる。シミュレーションのタイマーは定義した時計に従い、一時停止・リセットで実機保護を弱めない。履歴再生から過去のモーター指令を実機へ再送しない。

定量的な閾値は本案で仮に作らない。対応PC・機体、経路条件、運用範囲を選び、検証前に基準を設定して測る。一度動いたことだけで反復性を確認済みとしない。

## 6. 学生と基盤の分担・可変点

| 関心事 | 基盤が提供 | 学生が選択・実装 |
| --- | --- | --- |
| 移動 | 位置推定、経路実行、進捗・停止の契約 | 行先、巡回順、到着後の動作 |
| 認識 | 入力アダプタ、検証済み観測、差し替え可能な認識器 | 対象、サービス上の判定条件、反応 |
| 対話 | 依頼・確認・通知の仕組みと画面例 | 役割、文言、画面遷移、完了条件 |
| 実行 | 開始条件の仕組み、重複起動制御、並行活動の寿命、イベント配送、処理制御 | 起動条件、行動順、イベントへの反応、業務上の復旧方針 |
| 業務データ | 選択肢・フォーム入力、検証・再確認、構造化した値のサービスへの受け渡し | 本→棚・物品→箱の対応表、メニュー・注文、空席状態、行先・応答の解決 |
| 案件 | ID、状態、重複処理の仕組み | 状態の意味と業務遷移 |
| 試験 | 入力、Simulator接続、診断、再現シナリオ | 期待結果、実験、利用価値の評価 |

初期シナリオは固定リスト・対応表で代表できる。汎用検索エンジン、図書館DB、清掃・注文・貸出それぞれの固定状態機械を基盤へ要求しない。対象から行先を決める処理、到着時の棚段などの情報、対象なし・スタッフ案内の方針はサービス側に置く。

会場マップ、マーカー配置、カメラ校正、機体設定、運用制限は教員側の環境準備に含め、各班で再発明しない。

可変点は機体、認識器・入力、位置推定・移動方式、完了確認、開始条件、画面・通知先、実行ホスト、ミドルウェア、Simulator。まず代表的な一構成を実装する。必要能力と代替動作を明示し、全組合せを約束したり、実機能力を黙って疑似入力に置換したりしない。

## 7. 制約と設計候補

以下はアーキテクチャ比較への入力であり、追加の機能要求ではない。

- 基準機体にはオドメトリを前提とし、精度とカメラ・マーカー校正の負担を調べる。
- ブラウザ外runnerを優先候補にし、画面切断・プロセス障害時の動作を決める。
- 構築済みLinux環境を優先候補にする。Windowsではシミュレーション・制御を同じWSL2内にまとめて配布する案を検証する。WSL導入、GPU互換性、復旧は別途確認する。
- 全チーム分の調達前に、準備済みチーム計算機を1台試す。ラズパイは候補であり、全認識処理を載せられるとは仮定しない。
- ROS 2はロボティクス部品の再利用の観点で評価する。mailboxだけのために必須としない。
- Godot・MuJoCoと箱庭の有無を比較する。画像取得と制御接続は早めに試し、精細な会場作成は後にする。
- 軽量なローカル開発・試験経路を残す。すべてのローカル開発にROS 2・LiDAR・実機を必須としない。
- サービス利用者向け画面、運用画面、開発画面の分離を維持する。

学生向け記法、イベント配送方式、プロセス境界、API、ROS 2／箱庭の採否は未決定。記法より先に振る舞いを定義する。

## 8. 初期範囲と後回しにすること

初めに物体1種類・登録経路によるS1の小さな一連の動作を通し、S2・S3で清掃専用の契約になっていないか確認する。設計中にも配布・描画・カメラの不確実な部分を試作する。

自動清掃・積み下ろし、屋外案内、任意環境のSLAM・経路計画、複数機体の配車最適化、専用状態機械エディタ、多数のバックエンド、写実的な環境は後にする。必要な拡張境界は保持する。

Kitは競技課題・評価規則・無人運用を規定しない。

## 9. アーキテクチャの確認前に詰める論点

1. S1〜S3で対象サービスの幅を代表できるか。不足する振る舞いは何か。
2. 会場・機体に必要な経路精度、マーカー間隔、停止性能、観測の鮮度はどの程度か。
3. 画面切断で何を継続・停止し、何を運用者の明示的な再開にするか。
4. イベントの順序、キュー上限、重複、過負荷をどう扱う必要があるか。
5. 再起動後にどの案件状態を残し、報告をどこへ保存するか。
6. 最低限のPC・スマホ構成と、教員・学生それぞれに残る準備作業は何か。
7. 目的の試験に必要な物理・センサー・画像の再現度はどの程度か。

次の成果物は、要求IDから責務・インターフェース・配置・検証へ対応付けたアーキテクチャ案とする。再利用部分、不足、必要な小実験を示し、最初から全技術を選び切ろうとしない。
